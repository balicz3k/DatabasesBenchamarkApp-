\section{Cel i zakres pracy}
% ══════════════════════════════════════════════════════════════════════

Celem projektu jest porównanie wydajności czterech systemów zarządzania bazami danych (SZBD) przy wykonywaniu operacji CRUD (Create, Read, Update, Delete) na dużych zbiorach danych. Analizie poddano:

\begin{itemize}[noitemsep]
    \item \textbf{2 systemy relacyjne}: PostgreSQL 16, MySQL 8.0
    \item \textbf{2 systemy nierelacyjne}: MongoDB 7 (dokumentowa), Redis 7 (klucz-wartość)
\end{itemize}

Zakres pracy obejmuje:
\begin{enumerate}[noitemsep]
    \item Zaprojektowanie schematu danych systemu szpitalnego (13 tabel relacyjnych, model dokumentowy MongoDB, struktury Redis).
    \item Implementację aplikacji testowej automatyzującej generowanie danych, wstawianie, benchmarki i analizę.
    \item Przeprowadzenie 24 scenariuszy testowych CRUD (6 na każdą operację) w trzech skalach: 10\,000, 100\,000, 500\,000 rekordów.
    \item Porównanie wydajności przed i po zastosowaniu indeksów.
    \item Analizę planów zapytań (EXPLAIN).
    \item Weryfikację hipotezy badawczej o wpływie indeksów na wydajność.
\end{enumerate}

\subsection{Hipoteza badawcza}

\textbf{H1: Indeksy a wydajność} -- Zastosowanie indeksów znacząco poprawia wydajność operacji SELECT kosztem spadku wydajności operacji INSERT i UPDATE.

\section{Opis wybranych systemów zarządzania bazami danych}
% ══════════════════════════════════════════════════════════════════════

\subsection{PostgreSQL 16}

PostgreSQL jest zaawansowanym, obiektowo-relacyjnym systemem baz danych o otwartym kodzie źródłowym. Oferuje pełną zgodność z ACID, zaawansowane mechanizmy indeksowania (B-tree, Hash, GIN, GiST, BRIN), obsługę JSON/JSONB, widoki zmaterializowane, partycjonowanie tabel oraz replikację logiczną i strumieniową.

\textbf{Zalety}: Zaawansowane typy danych, rozbudowany optymalizator zapytań, pełna zgodność ze standardem SQL, doskonała obsługa transakcji, MVCC (Multi-Version Concurrency Control), wsparcie dla procedur składowanych w wielu językach (PL/pgSQL, PL/Python).

\textbf{Wady}: Wyższe zużycie pamięci w porównaniu z MySQL, wolniejsze wstawianie danych masowych bez odpowiedniej konfiguracji, bardziej złożona konfiguracja.

\textbf{Zastosowania biznesowe}: Systemy finansowe, systemy ERP, analityka danych, systemy GIS (PostGIS), platformy e-commerce.

\subsection{MySQL 8.0}

MySQL jest najpopularniejszym relacyjnym systemem baz danych o otwartym kodzie. Wykorzystuje silnik InnoDB z obsługą transakcji ACID, mechanizmem MVCC, kluczami obcymi i indeksami B-tree. MySQL 8.0 wprowadził okna analityczne, CTE (Common Table Expressions) i ulepszony optymalizator.

\textbf{Zalety}: Wysoka wydajność operacji odczytu, łatwość konfiguracji, szeroka kompatybilność, duża społeczność, niskie wymagania sprzętowe.

\textbf{Wady}: Ograniczone wsparcie dla zaawansowanych typów danych, brak niektórych funkcji SQL standardu (np. pełna obsługa sekwencji), historycznie słabsza optymalizacja podzapytań.

\textbf{Zastosowania biznesowe}: Aplikacje webowe (WordPress, Joomla), systemy CMS, platformy SaaS, systemy logistyczne.

\subsection{MongoDB 7}

MongoDB jest dokumentową bazą danych NoSQL, przechowującą dane w formacie BSON (Binary JSON). Oferuje elastyczny schemat, replikację zestawów replik (Replica Sets), sharding dla skalowalności horyzontalnej oraz zaawansowane indeksowanie (pojedyncze, złożone, wielokluczowe, tekstowe, geoprzestrzenne).

\textbf{Zalety}: Elastyczny schemat (schema-less), naturalne modelowanie danych hierarchicznych, szybkie operacje na pojedynczych dokumentach, łatwa skalowalność horyzontalna, wbudowana agregacja.

\textbf{Wady}: Brak transakcji wielodokumentowych (do wersji 4.0), większe zużycie pamięci dyskowej, brak JOIN (wymaga denormalizacji lub \$lookup), ewentualna spójność w konfiguracjach rozproszonych.

\textbf{Zastosowania biznesowe}: Systemy zarządzania treścią, aplikacje mobilne, IoT, katalogi produktów, systemy analityki czasu rzeczywistego.

\subsection{Redis 7}

Redis (Remote Dictionary Server) jest bazą danych typu klucz-wartość działającą w pamięci RAM. Obsługuje struktury danych: stringi, hashe, listy, zbiory, zbiory uporządkowane, strumienie. Oferuje persystencję (RDB, AOF), replikację master-slave i klaster Redis.

\textbf{Zalety}: Ekstremalnie niska latencja ($<1$~ms), bogate struktury danych, atomowość operacji, Pub/Sub, obsługa TTL (Time-To-Live), skrypty Lua.

\textbf{Wady}: Ograniczona pojemność (limitowana pamięcią RAM), brak złożonych zapytań (brak SQL), brak relacji między danymi, utrata danych w razie awarii (zależy od konfiguracji persystencji).

\textbf{Zastosowania biznesowe}: Cache'owanie, sesje użytkowników, kolejki wiadomości, tablice wyników w grach, systemy czasu rzeczywistego, liczniki i metryki.

\subsection{Modele danych w systemach nierelacyjnych}

\textbf{MongoDB} -- model dokumentowy z zagnieżdżeniami:
Pacjent jest dokumentem głównym, zawierającym tablicę wizyt, a każda wizyta posiada zagnieżdżone tablice: wykonane usługi, diagnozy, recepty (z pozycjami) oraz wyniki badań. Taki model eliminuje konieczność JOINów.

\textbf{Redis} -- model klucz-wartość:
Statusy wizyt przechowywane jako stringi (\texttt{visit:status:<id>}), sesje lekarzy jako hashe (\texttt{session:doctor:<id>}). Redis wykorzystywany jako warstwa cache i szybkiego dostępu.

\section{Opis aplikacji testowej}
% ══════════════════════════════════════════════════════════════════════

\subsection{Wymagania}

\begin{itemize}[noitemsep]
    \item Automatyczne generowanie syntetycznych danych medycznych przy użyciu biblioteki Faker.
    \item Masowe wstawianie danych (Bulk Insert) do 4 systemów bazodanowych.
    \item Wykonanie 24 scenariuszy CRUD w trybie bez indeksów i z indeksami.
    \item Pomiar czasu operacji (średnia z 3 prób) z~dokładnością do mikrosekundy.
    \item Automatyczne generowanie raportów EXPLAIN i wykresów porównawczych.
\end{itemize}

\subsection{Wykorzystane technologie i narzędzia}

\begin{itemize}[noitemsep]
    \item \textbf{Python 3.13} -- język implementacji aplikacji.
    \item \textbf{Docker + Docker Compose} -- konteneryzacja wszystkich 4 baz danych.
    \item \textbf{psycopg2} -- sterownik PostgreSQL.
    \item \textbf{mysql-connector-python} -- sterownik MySQL.
    \item \textbf{pymongo} -- sterownik MongoDB.
    \item \textbf{redis-py} -- sterownik Redis.
    \item \textbf{Faker} -- generowanie realistycznych danych syntetycznych.
    \item \textbf{pandas + matplotlib} -- analiza wyników i wizualizacja.
    \item \textbf{\LaTeX} -- skład sprawozdania.
\end{itemize}

\subsection{Struktura projektu i opis działania}

\begin{lstlisting}[language=bash,caption={Struktura katalogów projektu}]
ZTDB/
  docker-compose.yml       # 4 kontenery: PostgreSQL, MySQL, MongoDB, Redis
  run_all.py               # Glowny skrypt automatyzacji
  core/
    database.py            # ConnectionManager, wzorzec Abstract Factory
    generator.py           # DataGenerator - generowanie danych Faker
    seeder.py              # DatabaseSeeder - bulk insert, indeksy, schemat
    benchmark.py           # BenchmarkEngine - 24 scenariusze CRUD
  results/
    results_all.csv        # Zbiorczy plik z wynikami
    explain_report.txt     # Plany zapytan EXPLAIN
    charts/                # Wykresy PNG
  sprawozdanie/
    sprawozdanie.tex       # Niniejsze sprawozdanie
\end{lstlisting}

Aplikacja działa w pełni automatycznie. Polecenie \texttt{python run\_all.py} kolejno:
\begin{enumerate}[noitemsep]
    \item Sprawdza połączenia z~4 bazami danych (ping).
    \item Dla każdej skali (10k, 100k, 500k):
    \begin{enumerate}[noitemsep]
        \item Generuje dane w pamięci (Faker).
        \item Wstawia dane do PostgreSQL, MySQL, MongoDB, Redis.
        \item Usuwa indeksy, wykonuje benchmark (24 scenariusze $\times$ 3 próby).
        \item Tworzy indeksy, wykonuje benchmark ponownie.
        \item Generuje raporty EXPLAIN.
    \end{enumerate}
    \item Łączy wyniki CSV i generuje wykresy porównawcze.
\end{enumerate}

READ   & $-97\%$ & $-16\%$ & $-46\%$ & $-2\%$ \\
UPDATE & $-88\%$ & $+7\%$ & $-57\%$ & $0\%$ \\
DELETE & $-88\%$ & $-25\%$ & $-2\%$ & $-4\%$ \\
\bottomrule
\end{tabular}
\end{table}

\textbf{Kluczowe obserwacje:}
\begin{itemize}[noitemsep]
    \item PostgreSQL zyskuje najbardziej na indeksach -- operacje READ przyspieszyły o~\textbf{97\%} (z~16.61~ms do 0.57~ms dla 500k).
    \item W PostgreSQL nawet operacje CREATE przyspieszyły (mniej czasu na walidację FK z indeksem).
    \item MongoDB: READ przyspieszył o~46\%, UPDATE o~57\% -- indeksy na zagnieżdżonych polach dokumentu działają efektywnie.
    \item Redis jest niezmiennie szybki niezależnie od indeksów (O(1) dla operacji klucz-wartość).
    \item MySQL wykazuje niejednorodne wyniki -- CREATE wolniejsze z~indeksami (+23\%), co potwierdza koszt utrzymania indeksów.
\end{itemize}

\section{Weryfikacja hipotezy badawczej}
% ══════════════════════════════════════════════════════════════════════

\textbf{H1}: \textit{Zastosowanie indeksów znacząco poprawia wydajność operacji SELECT kosztem spadku wydajności operacji INSERT i UPDATE.}

\subsection{Analiza wyników}

\begin{table}[H]
\centering
\caption{Weryfikacja hipotezy -- PostgreSQL, skala 500\,000}
\label{tab:hypothesis}
\small
\begin{tabular}{@{}lrrr@{}}
\toprule
\textbf{Operacja} & \textbf{Bez indeksów [ms]} & \textbf{Z indeksami [ms]} & \textbf{Zmiana} \\
\midrule
CREATE (INSERT) & 18.90 & 2.58 & $-86\%$ (przyspieszenie) \\
READ (SELECT) & 16.61 & 0.57 & $\mathbf{-97\%}$ (przyspieszenie) \\
UPDATE & 7.69 & 0.95 & $-88\%$ (przyspieszenie) \\
DELETE & 20.78 & 2.48 & $-88\%$ (przyspieszenie) \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Wnioski dotyczące hipotezy}

Hipoteza H1 została \textbf{częściowo potwierdzona}:

\begin{enumerate}[noitemsep]
    \item \textbf{Potwierdzenie}: Operacje READ (SELECT) zyskały najwyższe przyspieszenie -- \textbf{97\%} w PostgreSQL dla skali 500\,000. Indeksy eliminują konieczność sekwencyjnego skanowania (Seq Scan) na rzecz skanów indeksowych (Index Scan, Bitmap Index Scan).

    \item \textbf{Odrzucenie części hipotezy}: Wbrew oczekiwaniom, operacje INSERT i UPDATE w PostgreSQL \textbf{również przyspieszyły} po zastosowaniu indeksów. Wynika to z~faktu, że scenariusze INSERT obejmują wstawianie rekordów z~kluczami obcymi -- indeksy na kolumnach referencyjnych przyspieszają walidację FK. Ponadto operacje UPDATE korzystają z~indeksów do szybszego lokalizowania aktualizowanego wiersza.

    \item \textbf{MySQL potwierdza hipotezę}: W MySQL operacje CREATE są wolniejsze z~indeksami (+23\%), co jest zgodne z~klasycznym kompromisem indeks vs. zapis. Każdy INSERT wymaga aktualizacji 16 dodatkowych struktur indeksowych.

    \item \textbf{Redis}: Niezależny od indeksów -- operacje O(1) na strukturach klucz-wartość.
\end{enumerate}

\section{Rozszerzona analiza wyników}
% ══════════════════════════════════════════════════════════════════════

\subsection{Skalowalność}

Na podstawie wykresu skalowalności (Rysunek~\ref{fig:scalability}) można zaobserwować:

\begin{itemize}[noitemsep]
    \item \textbf{Redis}: Stały czas operacji niezależnie od rozmiaru danych ($\sim$0.4~ms). Potwierdza złożoność O(1) operacji klucz-wartość.
    \item \textbf{MongoDB}: Liniowy wzrost czasu READ i UPDATE wraz ze wzrostem danych (bez indeksów). Z~indeksami wzrost jest minimalny.
    \item \textbf{PostgreSQL}: Bez indeksów -- gwałtowny wzrost czasu READ (od 1.07~ms do 16.61~ms dla 50x większych danych). Z~indeksami -- prawie stały czas.
    \item \textbf{MySQL}: Relatywnie stabilne czasy CREATE/UPDATE niezależnie od skali (buforowanie InnoDB).
\end{itemize}

\subsection{Porównanie modeli danych}

\textbf{Model relacyjny} (PostgreSQL, MySQL):
\begin{itemize}[noitemsep]
    \item Wymaga JOINów, ale z~indeksami osiąga doskonałą wydajność.
    \item Silne gwarancje spójności (ACID, klucze obce).
    \item Lepszy dla złożonych zapytań analitycznych.
\end{itemize}

\textbf{Model dokumentowy} (MongoDB):
\begin{itemize}[noitemsep]
    \item Eliminuje JOINy dzięki zagnieżdżeniom.
    \item Szybsze odczyty pojedynczych dokumentów.
    \item Wolniejsze UPDATE na zagnieżdżonych tablicach (szczególnie update\_many).
\end{itemize}

\textbf{Model klucz-wartość} (Redis):
\begin{itemize}[noitemsep]
    \item Najszybszy dla prostych operacji CRUD.
    \item Brak możliwości złożonych zapytań.
    \item Idealny jako warstwa cache.
\end{itemize}

\subsection{Dane półustrukturalne (JSON)}

MongoDB przechowuje dane w formacie BSON (Binary JSON), co stanowi wykorzystanie danych półustrukturalnych w projekcie. Dokumenty pacjentów zawierają zagnieżdżone tablice wizyt, diagnoz, recept -- bez sztywnego schematu. PostgreSQL również obsługuje JSON/JSONB, jednak w~tym projekcie skupiono się na modelu relacyjnym z~normalizacją.

\subsection{Automatyzacja testów}

Projekt realizuje pełną automatyzację:
\begin{itemize}[noitemsep]
    \item Jeden skrypt \texttt{run\_all.py} uruchamia kompletny pipeline benchmarkowy.
    \item Automatyczne generowanie danych, wstawianie, testy, raporty i wykresy.
    \item Parametryzowalne skale: \texttt{python run\_all.py --scales 10000 100000 500000}.
    \item Wyniki zapisywane w~formacie CSV, wykresy w~PNG, raport EXPLAIN w~TXT.
\end{itemize}

\section{Podsumowanie i wnioski}
% ══════════════════════════════════════════════════════════════════════

\begin{enumerate}
    \item \textbf{Redis} jest bezkonkurencyjnie najszybszy dla prostych operacji CRUD ($\sim$0.4~ms), ale nie nadaje się do złożonych zapytań relacyjnych.

    \item \textbf{PostgreSQL z~indeksami} oferuje najlepszy stosunek wydajności do funkcjonalności -- operacje READ w~0.57~ms nawet przy 500\,000 wizytach, zachowując pełne ACID i~integralność referencyjną.

    \item \textbf{MongoDB} sprawdza się doskonale dla odczytów pojedynczych dokumentów i~systemów o~elastycznym schemacie, ale operacje UPDATE na zagnieżdżonych strukturach są kosztowne przy dużych zbiorach.

    \item \textbf{MySQL} wykazuje stabilną wydajność niezależnie od skali, ale jest wolniejszy od PostgreSQL w~operacjach z~wieloma JOINami.

    \item \textbf{Indeksy są kluczowe} dla wydajności systemów relacyjnych -- przyspieszają READ o~nawet 97\%, a~w PostgreSQL przyspieszają również operacje zapisu (dzięki szybszej walidacji FK).

    \item \textbf{Wybór SZBD} powinien być podyktowany charakterem aplikacji:
    \begin{itemize}[noitemsep]
        \item Złożone zapytania analityczne $\rightarrow$ PostgreSQL
        \item Proste aplikacje webowe $\rightarrow$ MySQL
        \item Elastyczny schemat, agregacje $\rightarrow$ MongoDB
        \item Cache, sesje, kolejki $\rightarrow$ Redis
    \end{itemize}
\end{enumerate}
